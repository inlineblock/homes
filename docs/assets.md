# Reusable assets

An asset is something reusable across homes: a tile and its real-world dimensions, a material, a window, a cabinet module, a stool, a pendant light, a plant, or an entire assembly.

Use `library/<category>/<asset-name>/v001/`. Each version contains `asset.json`, editable source or a reproducible generator, and a preview when available. Texture sets belong alongside their material rather than in a global pile of images.

Record a stable ID, version, dimensions in meters, source/author, license or rights status, files, and any dependencies. Materials should record physical scale; texture maps should be identified as base color, roughness, normal, displacement, and so on. Models use meters and Z-up, with a sensible placement origin. Do not embed absolute paths to someone's Downloads folder.

Prefer linking reusable Blender collections and materials from their library file. Store those links as relative paths. Record the exact library version in the home's `project.json`. Do not edit a version that has been adopted by a home: make `v002`, review it, and explicitly update homes that should receive the change. Git history provides a second layer of traceability.

The first original asset is `materials/sage-fluted-tile/v001`: a 3 × 12 inch glazed, vertically ribbed ceramic tile. Its source geometry and material are generated by the shared tools and linked into Atrium 01. This is an original concept material, not a claim of a purchasable manufacturer's product.

Timber Courtyard 02 reuses that tile, the `fixtures/opal-globe-pendant/v001` and `furniture/walnut-counter-stool/v001` collections promoted from Atrium 01, and adds `materials/warm-vertical-cedar/v001` and `materials/charcoal-standing-seam/v001`. The new shaders accompany real board and seam geometry in the home's generator. The shared planting helpers create original geometry without external texture downloads.

For purchased or downloaded assets, record the original URL and actual redistribution terms. Where sharing the source is not allowed, store acquisition instructions and a placeholder rather than the restricted file.

## Required selection and contribution workflow

Before building a home, inventory its materials, planting, paving, hardware, lighting, cabinetry, furniture and equipment. Search the visual catalog and `asset.json` files. Record the chosen ID/version, role, placement and dependencies in the home's `assets/README.md` and `project.json`.

**Use an existing asset** when dimensions, mounting origin, front direction, clearances, material and rights fit. Link collections/materials with repository-relative paths. Generic generator helpers are useful, but copying their output into every home is not equivalent to adopting a shared asset.

**Clone and modify deliberately.** Never overwrite an adopted version. Use the next version for revisions to the same component identity; use a new descriptive slug for a distinct size/type/option that should coexist. Add `derived_from` with original ID/version, document the changed dimensions/interfaces and why the variation is needed, and preserve attribution and compatible rights. For a local experiment, use the home's ignored work area; publish the reusable result after review. A fork is not an excuse to erase the upstream origin.

**Contribute the finished variation back.** Include editable Blender source or deterministic generator; measured meter dimensions; origin and front direction; mounting and allowed scaling; installation/operating/service clearance assumptions; exact dependency versions; original/third-party rights; and an actual native preview. Label generic concept fixtures honestly instead of inventing a commercial specification. Reopen the asset in a clean process, inspect it in isolation and installed in the host, then adopt the new version explicitly. Record evidence and actual use; a file sitting unused in the library is not proof of reuse.

**Choose options by purpose.** Hardware families include knobs, bar pulls, edge pulls, door levers and flush pulls in multiple finishes. Lighting includes recessed downlights, task bars and focal fixtures. Appliances include cooktop, oven, dishwasher, hood, panel-ready wide refrigerator and fireplace; a separate tub is also shared. Clearances, recesses, ducts, flues and service spaces belong to the host design. Do not shrink a standard appliance or skip a ceiling opening to make an asset visually fit.

Coastal and Mountain now adopt shared planting, paving and storage collections in addition to shared materials/fixtures. The current catalog pins reviewed grass and shrub v002; earlier immutable versions remain traceable dependencies. Each home records its actual selected versions, and future adoption remains explicit.

### Operating-envelope metadata

For a cabinet, appliance or moving fixture, record the modeled state, intended open angle or travel, clearance envelope dimensions/origin, the basis of those values, and the host check. For example, an original cabinet may record `state: closed`, `opening_basis: concept door geometry`, and `host_open_state_checked: false` until its swept volume is actually checked. A closed preview is not evidence that doors open in the room. Manufacturer clearances should identify the exact product/manual rather than inherit an unrelated generic asset's assumptions.

If a requested parent asset does not exist, say so. Derive from the nearest suitable real source or create a new original asset, and record the true provenance; never claim an unavailable source size/version was cloned.

### Explicit native collection selection

When a native asset file also contains a preview studio, declare the reusable collection in `asset.json` under `blender.collection` (or the existing top-level `collection` convention). Host tools must select that name rather than the first collection returned by Blender; the first may be a studio wall, light or camera. `common.library.linked_collection` honors the declaration and rejects ambiguous legacy files. A preview studio must never become part of the installed fixture.
