# Home projects

- One home per folder. Begin with `project.json` and README; use `templates/home` for a new project.
- Keep editable sources in `model/`, presentation deliverables in `outputs/`, reference notes in `references/`, and unique assets in `assets/`.
- Store reusable content in the library and pin its version in `project.json`. Use relative links so a clone on another computer works.
- A layout change must update both the model and its outputs/plans/area schedule. Explain whether area includes walls, atria, porches, or garages.
- Keep rooms accessible, model door/window openings, and check circulation and furniture clearances. Do not count furniture placement as a resolved architectural layout.
- Apply `docs/home-design-standard.md` before rendering and again against the finished native model and plan. Every bedroom requires modeled usable clothes storage as a repository design requirement. Do not imply this is a universal legal definition of a bedroom.
- Draw the arrival sequence from road/parking to entry to public living space. Provide coat/drop storage, a generous arrival space, daylight where practical, and a clear sightline; reject unnecessarily long narrow entrance tunnels even when minimum circulation checks pass.
- List each repeated asset family in `assets/README.md`: pinned library ID/version, placements/use, and new-versus-reused status. Model, plan, project manifest and this schedule must agree. Bespoke exceptions require a concrete geometric/design reason; plants and standard pavers are not automatically bespoke because their placement differs.
- New and substantially revised homes must include front/arrival, rear/outdoor living, and a side or elevated view that explains roof, parking and site relationship, plus plans showing closets and circulation. Check these views against one another.
- Preserve approved versions through Git; make reviewed changes on branches when collaboration is active. Coordinate edits to binary files.

## Required output organization
- Every home must have `outputs/README.md` as its visual index, `outputs/images/` for selected model renders, and `outputs/plans/` for PDFs, presentation boards, vector plans, and their PNG previews.
- Keep only the current reviewed result for each view or document. Regenerate into the same descriptive filename; do not create dates, `v001`, `history/`, `archive/`, `final-final`, or duplicate “latest” folders for outputs. Numeric view prefixes indicate different views, not revisions. Git retains previous revisions.
- Put experiments and unreviewed iterations in ignored `outputs/work/` or outside the repo. Visually inspect results before promoting them to the published output paths; a successful command alone does not make an image reviewed.
- Follow the required visual gallery below in the home README, outputs index and root project catalog. A single hero image plus an external gallery link is insufficient.
- Keep `project.json` deliverable paths, authoring tools, saved Blender render destinations, and all documentation aligned with this structure. Never leave a second copy in legacy `renders/` or `drawings/` folders.
- Editable models stay in `model/`. Shared library asset versions remain a separate dependency convention; do not add version folders to home outputs.
- Original designs, models, and outputs use CC BY 4.0; authoring code uses MIT. Preserve attribution and reference exclusions in `LICENSE.md`.

## Required visual gallery
- Each home page and output index must lead with a reviewed **Imagegen photographic study as the first image**, before the native gallery. Preserve the source design and viewpoint, inspect for invented architecture/site features, and correct material drift. Save the selected study under `outputs/images/` with a stable descriptive filename and its actual prompt/provenance under `outputs/`. Keep existing native renders and editable models intact.
- Label that first image as an AI photographic study, not an existing-building photograph or exact model evidence. Record it in `gallery.json` under `photographic_hero`, outside `renders`, with source-render path/hash, selected-image hash and provenance path. It must not satisfy native-render counts or signature-feature validation. The root catalog should likewise lead each project with this image while retaining all required native coverage. When the source view changes, refresh or explicitly retire its derived study.
- For requested interior Imagegen studies, pair each with its reviewed native interior source on the home page, outputs index and catalog. Register them separately under `photographic_interiors` with the same provenance/hash fields as the exterior hero; they do not count toward native coverage. Refresh the pair when that room changes.
- Every completed home gallery must directly embed at least **five distinct reviewed native renders**, comprising **three exterior angles** (front/arrival, rear/outdoor living, and side or elevated roof/site relationship) and **two useful interior views**. Five is a floor, not a cap. Show additional rooms and angles when they explain the design; alternate crops or lighting of one camera do not replace missing coverage.
- Embed a legible furnished floor-plan PNG for **every occupied level**, in addition to those five renders. Link the editable plan and available PDF. A roof-off model view or a tiny plan on a presentation board does not replace a readable floor plan.
- Every defining feature needs a dedicated, clearly captioned image: for example a pool, exceptional fireplace, courtyard, wraparound deck, pool-table room, parking lift, or indoor/outdoor serving counter. The feature must be clearly visible rather than merely mentioned or glimpsed in the background. Existing coverage may satisfy this when the feature is the subject. Show paired operating states for moving features where needed to explain them.
- The home's `README.md` and `outputs/README.md` must embed all selected current renders and each level's plan, with meaningful captions. Keep the main README useful to someone who never opens another page. The root README must include the same minimum coverage and defining-feature previews for each project, with links to the full home and output index; use compact image grids there.
- Maintain `gallery.json` in each home: current render paths, captions, view category, exterior role, required occupied levels, floor-plan paths and named signature features with their image paths. Paths are relative to the home. Register only real, reviewed files; do not invent images to satisfy a count.
- Run `python3 tools/common/verify_galleries.py` after editing galleries or renaming outputs. This verifies files, unique coverage, levels, feature links and actual embedded images in all three README locations. It does not assess the pictures: inspect the actual pixels for useful composition, consistent architecture, readable plans and truthful captions before declaring the gallery complete.
- If coverage is missing, render the missing view from the current native scene, review it in ignored `outputs/work/`, then promote it to a stable filename and update native/source camera definitions and deliverable paths. Do not substitute generated illustrations or count cutaways as exterior photographs. Preserve the approved design during a camera-only task; report design defects separately.
